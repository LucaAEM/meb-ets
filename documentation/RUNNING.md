# Running the archived engines

## Status and provenance

RUN_MESE_v7.R and RUN_MESE_EMPIRICAL.R are newly prepared distribution launchers. They are not byte-identical copies of the historical launchers and have not been executed in R during packaging. They retain the original engines and expose their existing stages. Their own metadata distinguish new replication runs from historical results. Hash checks enforce the two archived engine versions.

The default stage is `check`. It does not fit models, generate bootstrap series or simulate futures. The empirical check does load the dataset and construct the task manifest. Sourcing the launchers executes their selected stage: review the first lines before sourcing them.

## Environment

Use a fresh R session with the repository root as the working directory. The recorded environment used R 4.4.3, forecast 8.23.0 and meboot 1.4.9.4. Tourism data were loaded using Tcomp 1.0.1. Install dependencies explicitly in an environment you manage; the launchers do not install or update packages. The core enforces the forecast and meboot versions. Record sessionInfo() and inspect package/data hashes; do not assume exact reproduction under different dependencies.

## Lightweight checks

From the repository root in R:

```r
source("RUN_MESE_v7.R")
source("RUN_MESE_EMPIRICAL.R")
```

Alternatively:

```text
Rscript RUN_MESE_v7.R
Rscript RUN_MESE_EMPIRICAL.R
```

Leave RUN_STAGE = "check" for these checks. Passing them does not demonstrate calibration, convergence of simulation budgets or optimization adequacy.

## Simulation stages

Edit RUN_STAGE in RUN_MESE_v7.R:

- timing: small workload with all method groups;
- precision: the archived pilot configuration, B up to 200 and S up to 4000;
- validation: the archived schedules, B = 100 and S = 2000;
- collect: read an existing result directory specified explicitly in COLLECT_FOLDER.

Validation requires explicit CONFIRM_VALIDATION, PROTOCOL_FROZEN and PRECISION_CHECKED confirmations and a nonempty, accurate VALIDATION_APPROVAL_NOTE. Do not assert completion of a new precision pilot merely because historical summaries are available. A targeted historical S = 10000/20000 pilot is not generated by the standard precision stage. Actual configuration values govern the run, not prose in an approval note.

New runs go under replication_runs/simulation/. Changing an engine or configuration is not compatible with resuming arbitrary historical checkpoints. Preserve original results separately and use a new directory for a new protocol. No stage starts the next automatically.

## Empirical stages

Edit RUN_STAGE in RUN_MESE_EMPIRICAL.R:

- pilot: six training-metadata-selected series, B = 10, S = 500;
- full: monthly Tourism population, B = 100, S = 20000, requiring CONFIRM_FULL_RUN = TRUE;
- collect: read a specified existing empirical result directory.

Keep DATASET = "tourism_monthly" and ORIGIN_OFFSETS = 0L for the reported design. New runs go under replication_runs/empirical/. The engines also expose alternatives, but changing them creates a different experiment. Do not relabel Tourism as M3 or a single origin as rolling-origin.

## Collection and audits

Collection performs no fitting but may write derived summaries. It is not a read-only integrity audit. Use stable completed result folders, and do not collect while an audit is checking input hashes. Original audit scripts and extraction scripts will be deposited separately; their hard-coded folder variables must point to the intended result folders. Some audits require fit checkpoints, which are not included in the curated summary tables.

## Cost and interpretation

Full runs can be expensive. Timing estimates from small pilots are not guarantees. Retry switches default to FALSE; failures remain visible. Native optimizer codes are not automatic missing forecasts or competitor defeats. Inspect all status and diagnostics before interpreting results. The scientific interpretation remains that of the manuscript and its documented limitations.
